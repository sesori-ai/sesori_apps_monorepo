# Desktop Automatic Updates

## Goal

Sesori Desktop updates itself silently on macOS and Linux, and on Windows before its
first public release. A new version downloads quietly and installs when the user quits
or clicks "Restart to update". Nobody visits the download page twice.

This supersedes desktop-distribution D4, D5 and D6 (manual-only updates, no embedded
updater), which the user reversed on 2026-10-25.

## Decisions (user-decided 2026-10-25)

| ID | Decision |
|---|---|
| U1 | Silent self-update on macOS and Linux is mandatory. Windows may compromise only if that keeps things simpler (it does not need to: Velopack is silent). |
| U2 | macOS: Sparkle 2 with an EdDSA-signed appcast, and automatic background download. It installs on Quit or "Restart to update". Keep the notarized DMG and ZIP. |
| U3 | Windows and Linux AppImage: Velopack. Its packager replaces Inno Setup and our AppImage builder. We wire in its C library through our own FFI, not the immature `velopack_flutter`. |
| U4 | Velopack only checks the SHA-256 listed in its own feed. Our Dart code verifies an Ed25519 signature on that feed before Velopack reads it, so writing to the bucket alone can never ship a build. |
| U5 | DEB/RPM: installing the package registers its repository (#2051). The DEB also opts the Sesori origin into unattended-upgrades. RPM relies on the system's automatic updater where it is enabled. The app notices when its files were replaced and offers "Restart to update". |
| U6 | Updates are on by default, with a Settings toggle. Off means no background check; Settings keeps "Check for updates". |
| U7 | One new Ed25519 update key, generated by the user and stored as a secret. Agents never see the private key. The public key is compiled in. Sparkle's EdDSA and our feed signature use the same key. |
| U8 | Feeds are static per-channel, per-OS/CPU files on the existing GCS hosting. There is no release backend. |
| U9 | macOS installs from before Sparkle, and AppImages from before Velopack, need one last manual update. The phone sheet and the download docs say so (step 8). Those old builds keep their own Settings copy, which we cannot change. |
| U10 | The first public Windows release ships with Velopack. desktop-distribution steps 7–8 (signing, winget) now package Velopack's `Setup.exe` instead of Inno. |
| U11 | Engine choice: the user delegated it on 2026-10-25 against "silent update, simpler maintenance, good UX". Sunk cost does not count. Rejected: WinSparkle (not silent), the stale `auto_updater` plugin, and a custom Dart apply engine. |

## Current behaviour (origin/main `c7023ac28e`)

- `DesktopUpdateDestination` (`module_desktop_core/.../desktop_update_destination.dart`)
  is selected in `client/desktop/lib/core/desktop_update_configuration.dart` and rendered
  only by `desktop_update_section.dart` as a link or advice. Nothing checks for updates.
- The bundled bridge's own GitHub updater is disabled when supervised
  (`bridge/app/lib/src/updater/foundation/update_policy.dart`). It stays that way:
  the desktop updater owns the whole bundle, bridge included.
- Quit: `BridgeControlCubit.quit()` stops the helper, then the tray, window and process.
  The macOS Cmd+Q menu item uses stock `terminate:` with no `applicationShouldTerminate`
  hook, so it may skip `quit()`. Sparkle's relaunch uses the same terminate path.
- Single instance is a Dart `FileLock` (`DesktopInstanceApi`). Windows also has an Inno-only
  mutex marker in `windows/runner/main.cpp`.
- Packaging: `package_desktop_macos.py` (sign, notarize, DMG/ZIP),
  `package_desktop_windows.py` + `client/desktop/tool/windows_installer.iss` (unsigned,
  unpublished), and `package_desktop_linux.py` (DEB, RPM and `build_appimage`). Assets go to
  GitHub Releases; APT/RPM repositories go to `gs://sesori-ai-linux-packages`.
- `probe_sparkle.swift` typechecks against Sparkle 2.10.0 in `desktop-qualification.yml`.
  It is only a historical probe.
- The phone `showBridgeUpdateSheet` (`bridgeUpdateDesktop*` strings) gives manual
  download, quit and install steps.

## Design

### Packages touched

- **`client/module_desktop_core`** (steps 2, 4 and 6): update state, service, repository,
  APIs, the feed validator and the Velopack bindings. It gains `ffi`, `http` and
  `cryptography`.
- **`client/desktop`** (steps 2, 4 and 6): adapters for Layer-0 interfaces, `main`, the
  macOS runner (Sparkle and the terminate seam), the Windows runner (marker removal), and
  Settings and tray rendering.
- **`client/module_app_ui`** (step 8): the phone sheet strings.
- **`shared/sesori_shared`**: only the `health_response.dart` comment.
- **`.github/` workflows and scripts** (steps 2, 3, 4, 5 and 7): packaging, signing and
  feed publication.

### Layers (module_desktop_core)

```text
foundation/  (Layer 0, dumb seams)
  DesktopInstallKind { macosSparkle, velopack, linuxPackage, development }
    resolved once from shell-provided facts: compiled identity define, channel define, APPIMAGE
  SparkleUpdateEngine (interface)   setAutomaticChecks(enabled:), checkNow(),
                                    downloadedVersions: Stream<String>
    implemented once in client/desktop/lib/core/platform/ over a method channel
  VelopackBindings                  pure-Dart dart:ffi over Velopack.h; shell passes the library path
  InstalledDesktopBundleSource      compiled DesktopBundleIdentity + read installed desktop-bundle.json;
    implemented once in the shell; DesktopBridgeExecutablePathResolver is rebuilt on it (no copy)
  desktopUpdatePublicKey            compiled Ed25519 public key constant
  WindowHostEvent.quitRequested     native terminate request (macOS Cmd+Q, Sparkle relaunch)
  SystemTrayCommand.restartToUpdate

api/  (Layer 1)
  DesktopUpdateFeedApi              unauthenticated GET of feed, .sig and package
  VelopackUpdateApi                 API over Velopack's update manager; owns the staging dir it reads
  DesktopRelaunchApi                spawns /usr/bin/sesori-desktop --after-update (detached)
  DesktopInstanceStorage            + read/writeAutomaticUpdates (same shape as the attention preference)

repositories/  (Layer 2)
  DesktopUpdateRepository           fetch -> DesktopUpdateFeedValidator (Ed25519) -> stage -> Velopack
                                    file source check/download; maps engine events to DesktopUpdateState
  DesktopInstanceRepository         + automatic-updates toggle

services/  (Layer 3)
  DesktopUpdateService              owns states, toggle gating, one check() entry,
                                    prepareExit(intent: DesktopExitIntent { quit, restartToUpdate })

cubits/  (Layer 4)
  DesktopUpdateCubit                toggle + "Check for updates" rows
  BridgeControlCubit                quit()/restartToUpdate() call prepareExit instead of
                                    BridgeProcessService.stop(); subscribes to update states for the tray
```

`DesktopInstallKind` picks the engine inside the package. The shell registers one adapter
per Layer-0 interface. `resolveDesktopUpdateDestination` and `DesktopUpdateDestination`
are deleted.

```text
sealed DesktopUpdateState
  DesktopUpdateIdle
  DesktopUpdateReady(version)                  // verified; installs on Quit or "Restart to update"
  DesktopUpdateManagedBySystem                 // DEB/RPM until the installed bundle differs, then Ready
  DesktopUpdateUnavailable(DesktopUpdateUnavailableReason { developmentBuild, unwritableLocation })
```

### Exit and restart ownership

`DesktopUpdateService.prepareExit(intent:)` stops the helper through `BridgeProcessService`.
If the following engine step fails, it restarts the helper and reports the failure.

| Install kind | `quit` | `restartToUpdate` |
|---|---|---|
| velopack | If Ready: `vpkc_wait_exit_then_apply_updates(silent, restart: false)` | Same, with `restart: true` |
| macosSparkle | Nothing; Sparkle installs on normal termination | Sparkle install-and-relaunch |
| linuxPackage | Nothing | `DesktopRelaunchApi` |

`BridgeControlCubit` keeps tearing down the tray and window and calling `terminate`. It
never touches an engine.

Only one quit runs at a time, and nothing re-enters it.

- On macOS, `applicationShouldTerminate` answers `terminateLater` and emits `quitRequested`.
  `BridgeControlCubit` handles that like tray Quit.
- The macOS terminator replies through the channel rather than `io.exit`, so
  `NSApplicationWillTerminate` fires and Sparkle installs.
- A terminate request that arrives while a quit is running (Sparkle relaunch, a second
  Cmd+Q) is answered natively at once, without going back into Dart.
- `--after-update` is parsed in `desktop_launch_arguments.dart`. With it,
  `DesktopInstanceService` waits a bounded time for the primary lock before the existing
  "signal primary and exit".

### Checks and the toggle

- The toggle has one source of truth: `DesktopInstanceStorage`.
- **Sparkle:** Info.plist sets `SUEnableAutomaticChecks` and `SUAutomaticallyUpdate`, so
  Sparkle never shows its own permission prompt. The service pushes
  `setAutomaticChecks(enabled:)` at startup and on every toggle change.
- **Velopack:** `DesktopUpdateService` owns one trigger: a check at startup, then every 6
  hours, cancelled while the toggle is off.
- **Linux packages:** the same trigger compares the installed bundle with the compiled
  one, with no extra timer. "Check for updates" calls the same `check()`.

### Trust and feeds

- **macOS:** `appcast.xml` per channel and CPU. Each item's enclosure is the
  already-published, checksum-verified GitHub release ZIP, with a `sparkle:edSignature`
  over its bytes. The CI script signs with Python `cryptography` Ed25519, so we need no
  Sparkle `sign_update` binary in CI. The runner Info.plist carries `SUFeedURL` (set from
  the compiled channel and CPU) and `SUPublicEDKey`.
- **Velopack:** `vpk pack` output per channel and OS/CPU, with
  `releases.<channel>.json` plus `.sig`, and the full `.nupkg` on GCS. Dart fetches the
  feed and signature, verifies Ed25519 against the compiled key, and downloads the
  referenced full package. It writes both into Velopack's packages directory and runs
  `vpkc_new_source_file` on that directory. Velopack then checks the package SHA-256
  against the now-trusted feed. No sync FFI callbacks cross threads.
- Signing runs in a main-only job holding only the update-key secret. Upload is a
  separate job with the existing bucket-scoped federation, following the
  `linux-repository.yml` split.

### Linux

- The DEB ships `/etc/apt/apt.conf.d/52sesori-unattended-upgrades` containing
  `Unattended-Upgrade::Origins-Pattern { "origin=Sesori"; };`. It is a package-owned
  non-conffile, like #2051's files.
- The RPM ships nothing extra. `dnf-automatic` and GNOME Software apply to every enabled
  repository.
- AppImage: Velopack replaces the file in place at the same path, so the autostart entry
  that points at `$APPIMAGE` keeps working.

## Verification

Coverage level: **L5**. The delivered behaviour is packaged and external: a real
signed N→N+1 update through the public feed on each platform.

| Platform | Proof |
|---|---|
| macOS arm64 and x64 | An installed internal build N updates silently to N+1 on Quit and through "Restart to update". The bundled bridge's version matches after relaunch. |
| Windows x64 | Velopack Setup installs per-user. N→N+1 updates silently on Quit and on restart. Windows arm64 is blocked on the missing interactive host (desktop-distribution gate), which stays an explicit blocker. |
| AppImage x64 and arm64 (Ubuntu, Fedora, Arch) | Same path updated in place. Autostart keeps working. |
| DEB (Ubuntu) | unattended-upgrades installs N+1 with no prompt, and the running app offers "Restart to update". |
| RPM (Fedora) | `dnf-automatic` (where enabled) installs N+1, and the app offers "Restart to update". |
| Adverse | A tampered feed or package is refused (bad signature, wrong SHA). An unreachable feed stays idle without user-facing errors and logs locally. |

No extra native hosts are verified for the matrix. Missing hosts stay explicit blockers,
never silent reductions.

## Complexity budget

New mutable parts:

- one persisted boolean (the toggle);
- one in-memory `DesktopUpdateState` stream and one check timer, both owned by `DesktopUpdateService`;
- Velopack's own packages directory, owned by Velopack.

Deliberately not added:

- delta packages (full packages only, until size measurably matters);
- staged rollouts;
- download-progress UI;
- a rollback UI;
- a release backend;
- a custom apply engine;
- per-arch fallback feeds;
- update analytics, until a product question needs them.

## Risks and accepted limits

- **Operator authority needed for step 7:** the `linux-packages` federation provider
  must allow the feed-publishing workflow identity on the existing bucket (a prefix such
  as `desktop-updates/`). It is one condition edit, with no new bucket or service account.
  We will ask for this concretely before step 7.
- **User action for step 3:** generate the Ed25519 key and store it as the
  `DESKTOP_UPDATE_SIGNING_KEY` secret in a main-only environment
  (`desktop-update-signing`, no reviewers; production stays gated by `store-production`).
- **Velopack bus factor:** it has essentially one maintainer, and 1.0 arrived in May 2026.
  Mitigation: pin the version and verify the prebuilt library checksum. The FFI surface
  is small enough to swap later.
- **DEB/RPM silence depends on the distro:** Ubuntu enables unattended-upgrades by
  default. Where no automatic updater runs, updates arrive through the normal Software
  Updater prompt. We document this honestly and do not add a root helper.
- **Key rotation and compromise:** installed builds trust exactly one compiled
  public key.
  - *Rotation:* feed URLs include a key ID (for example `.../k1/<channel>/...`), and each
    build fetches the path for its own key. A release signed with k1 ships the k2 public
    key and the k2 feed path. After that, the k1 feeds stay frozen at that transition
    release. An install that was offline or had updates off during the transition still
    finds a k1-verifiable update, then continues on k2. Sparkle allows `SUPublicEDKey` to
    change through an update signed with the old key.
  - *Compromise:* stop publishing feeds, which removes the write path. Then rotate as
    above, and publish an advisory directing affected users to a manual reinstall from
    GitHub Releases. We don't add a multi-key trust list or revocation machinery up
    front.
- **Unwritable install locations** (for example a macOS app in a root-owned folder):
  Sparkle prompts for authorization. We accept that.

## Review record

`architecture-plan-review` (2026-10-25) rejected the first draft. Its findings were
applied directly:

- layered breakdown;
- one `prepareExit` owner;
- the macOS terminate seam and no re-entry;
- install-kind selection moved into the package;
- the shared installed-bundle seam;
- check and toggle ownership;
- the relaunch owner;
- native code and dependency placement;
- the named validator;
- `NoDesktopUpdater` dropped, with a typed reason;
- tray and cubit wiring;
- the list of packages touched.

For the package-manager change trigger, it offered a file watcher or the existing check
trigger. We chose the existing check trigger: one fewer moving part.
